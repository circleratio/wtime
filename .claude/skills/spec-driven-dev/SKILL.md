# spec-driven-dev

`wtime` プロジェクトでの開発は、以下の5段階を順に進める。各段階の成果物はファイルとして永続化し、次の段階の入力とする。段階を飛ばしたり、成果物を作らずに直接実装に進んだりしない。

```
要求仕様定義 → 設計 → 実装計画作成 → 実装 → ドキュメント作成
(doc/requirement.md) (doc/spec.md) (doc/plan.md)  (src/, tests/)  (README.md)
```

ユーザーから依頼されるのはこのうち1段階だけのことが多い（例:「実装して」だけ）。その場合でも、前段の成果物（`doc/requirement.md` や `doc/spec.md`）が存在すればそれを入力として使い、存在しなければ先に確認するか、必要最小限を補って進める。逆に、ユーザーが1段階しか頼んでいないのに他の段階まで勝手に進めない（例: 「要求仕様をまとめて」と言われただけで実装まで着手しない）。

## 1. 要求仕様定義（成果物: `doc/requirement.md`）

- 既存の `doc/requirement.md` を読み、概要・要求仕様・使いかたのセクションで**曖昧・空欄・矛盾している箇所**を洗い出す。
- 洗い出した不足点は、思い込みで埋めずに `AskUserQuestion` でユーザーに確認する。1問につき2〜4個の具体的な選択肢を用意し、妥当な既定案を先頭に置く（例: 出力フォーマットの選択肢をプレビュー付きで提示する）。
- 特に見落としやすい観点:
  - 概要に書かれている機能が「使いかた」セクションに反映されているか（今回、時差計算が概要にだけあり使いかたに無かった）
  - 出力フォーマットの具体例（日付・時刻・タイムゾーン表記など）
  - 複数入力（複数タイムゾーンなど）を許可するか
  - 異常系の挙動（不正な入力・終了コード）
  - CLIとしての付帯仕様（`--help`/`--version` など）
  - 実装言語やランタイムの制約
- 回答が揃ったら `doc/requirement.md` を直接編集して確定させる（別ファイルに書かない）。「要求仕様」セクションは箇条書きで確定事項を列挙し、「使いかた」セクションには確定した出力例をコマンド例として追記する。

## 2. 設計（成果物: `doc/spec.md`）

`doc/requirement.md` を入力に、実装方針を設計として言語化する。以下の観点を最低限含める。

- ディレクトリ構成（`src/wtime/` 配下のモジュール分割方針）
- モジュールごとの責務と主要な関数シグネチャ（実装前に決めておくことでブレを防ぐ）
- CLIの引数・オプション・終了コードの一覧表
- エラーハンドリング方針（どんな例外をどこで変換し、どんなメッセージ・終了コードにするか）
- 標準ライブラリだけで実現できない仕様（例: ローカルタイムゾーンのIANA名解決）は、複数のフォールバック手段を明記する
- パッケージング方針（`pyproject.toml` の構成、バージョン管理の一元化）
- テスト方針（何を単体テストで担保するか、境界値・異常系を含む）

`doc/requirement.md` にない仕様の詳細（内部的な関数名・データ構造など）はここで初めて決めてよい。ただし要求仕様と矛盾する設計をしない。

## 3. 実装計画作成（成果物: `doc/plan.md`）

`doc/spec.md` を入力に、実装順序をステップとして分解する。

- 各ステップに「やること」と「完了条件」を明記する（完了条件は基本的にテストや動作確認で検証可能なものにする）
- ステップ間の依存関係（並行実装可能な部分、後回しにできない部分）を明記する
- 最後に必ず「手動動作確認」のステップを入れる。`doc/requirement.md` の使用例と実際の出力を突き合わせる具体的なコマンド列を書く
- 最後に「最終確認」のステップを入れ、テスト全件成功と要求仕様との突き合わせを行う

## 4. 実装（成果物: `src/`, `tests/`）

`doc/plan.md` のステップを順に実施する。

- 実装中に計画からの逸脱が必要になった場合（例: 実行環境に `pip`/`pytest` が無くインストールできない、といった環境制約）は、代替手段（`unittest` へのフォールバックや `PYTHONPATH` 経由の実行など）を採用し、**何を・なぜ変更したかをユーザーに一言報告する**。ドキュメント側の記述もその場で実態に合わせて修正する。
- 実装が終わったら、`doc/spec.md` のテスト方針に沿ってテストコードを書き、テストを実行して全件成功させる。
- テストが通っただけで終わらせず、`doc/requirement.md` の使用例に書かれたコマンドを実際に実行し、出力が仕様通りであることを目視確認する（正常系・異常系の両方、終了コードも含む）。
- 生成された `__pycache__` や `.pytest_cache` などの副産物は作業完了時に削除する。

## 5. ドキュメント作成（成果物: `README.md`）

実装が完了したら、プロジェクトルートの `README.md` を実態に合わせて作成・更新する。

- 想定読者は「これから使う人／開発に参加する人」であり、`doc/spec.md` のような内部設計の詳細は書かない
- 最低限含める内容: 必要環境、インストール方法、使いかた（`doc/requirement.md` の使用例をベースに実際の出力例を添える）、開発者向けのテスト実行方法、`doc/` 配下のドキュメントへのリンク
- インストールに前提条件がある場合（例: `pip` が使えない環境での代替実行方法）は必ず書く。この判断は実装段階で得た実行環境の知見（ステップ4参照）を反映する
- ユーザーから「テスト実行方法は？」のような個別の質問が来た場合は、READMEの該当箇所を答えの根拠にしつつ、実際に手元で動くかどうかを踏まえて簡潔に回答する。README自体に古い記述が残っていないかもこの機会に点検し、必要なら直す

## 段階をまたぐときの原則

- 各段階の成果物ファイルは常に「今分かっている確定事項」を表す。ステップの途中経過や検討過程をファイルに書き残さない（それはチャットでの説明に留める）。
- 前段の成果物と矛盾する決定をする場合は、前段のファイルも合わせて更新し、後から読んでも一貫した記録になるようにする。
- 曖昧な要求を推測で進めるくらいなら、影響が大きい判断（出力フォーマット、異常系の扱い、対応範囲など）は `AskUserQuestion` で確認する。逆に、実装の詳細（変数名や内部関数の分割方法など）まで逐一確認する必要はない。
